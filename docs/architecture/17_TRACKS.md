# 17. Треки об'єктів між кадрами (як track у CVAT)

> Додано 2026-11-17 (гілка `tracks`). Рішення мейнтейнера: кадри = серія за назвою; проміжні кадри —
> інтерполяція; потрібні Outside, злиття/розділення, експорт з номерами треків. Інструкція для людей —
> `README.md` §«🎞 Треки». Код: `tracks.py`, `routes/api_tracks.py`, `static/modules/editor/tracks.js`.

## 1. Модель
- **Серія** = фото, чиї імена відрізняються лише числом у кінці: `cell_001, cell_002…` → серія `cell_`, кадри 1, 2…
  (`tracks.series_of`, regex `^(.*?)(\d+)$`). Порядок — за числом; беруться лише фото в `images/` (не `_excluded`).
  Фото без числа в кінці — серія з одного кадру. Трек ніколи не виходить за межі своєї серії.
- **SoT треків** — `<workspace>/tracks.json`: `{version, next_id, tracks: {"<id>": {label, series,
  keyframes: {"<stem>": {points, outside}}}}}`.
- **Форма на кадрі** (`shape_at`): до 1-го ключа — нема; останній ключ ≤ кадру — outside → нема; є наступний
  не-outside ключ → **інтерполяція** (`interpolate`: ресемплінг обох контурів до однакової к-сті точок за довжиною
  дуги, однаковий напрямок обходу, зсув старту з мінімальною сумою квадратів, лінійно по t); інакше — копія ключа
  (трек триває до кінця серії).
- **Матеріалізація**: на кожному кадрі форма треку — звичайний shape у `polygons/<stem>.json` з
  `flags = {track_id, keyframe}` → bake / groups / export / ghost працюють без змін (полігон треку = полігон).

## 2. Синхронізація (головний механізм)
`POST /api/polygons/<stem>` (кожен autosave / Save) після запису кличе `tracks.sync_frame`:
| На кадрі після збереження | Що стається з треком |
|---|---|
| shape з `track_id`, якого нема в tracks.json | новий трек: ключовий кадр тут, серія з імені |
| форма (допуск 1e-3 px) або клас відрізняються від розрахункової | ключовий кадр тут; зміна класу = клас усього треку |
| shape треку, видимого на цьому кадрі, ЗНИК | `outside` з цього кадру (клітина зникла) |
| без змін (у т.ч. матеріалізований кадр) | нічого (ключовий кадр НЕ створюється) |

Далі `materialize` перезаписує **інші** кадри серії (поточний щойно зберіг редактор). Відповідь `tracks:
{tracks, frames, states}` → фронт оновлює каталог і кеш прев'ю (`_tracksApplyServerResult`).

**Інваріанти (порушення = десинк груп):**
- оновлення полігона треку на кадрі — **на тому самому індексі** shape (`polygon_indices` груп не зрушуються);
  новий — у кінець; видалення (outside) — `splice` + ремап `groups/<stem>.json polygon_indices` (як фронтовий
  `_polyRemapGroupsAfterShapeDelete`);
- кадр, що отримав полігон треку і не має стану в selections.json, стає `manual` + dirty (інакше не запечеться);
  те саме для поточного кадру, якщо його розмічали з картки «Оригінал»;
- `tracks.json` і перезапис кадрів — під одним `threading.RLock` (Flask threaded).

## 3. Операції (`routes/api_tracks.py`)
| Запит | Дія |
|---|---|
| `POST /api/tracks/new` | зарезервувати номер (трек з'являється при збереженні кадру з цим `track_id`) |
| `GET /api/tracks` | список: id, label, series, keyframes, first/last видимий кадр, к-сть кадрів |
| `POST /api/tracks/<id>/split {stem}` | від кадру (включно) — новий трек; старий отримує outside на цьому кадрі |
| `POST /api/tracks/<id>/merge {from}` | `from` вливається: його видимі кадри стають ключовими для `<id>`, де той невидимий; outside-ключі `<id>` там, де видно `from`, замінюються формою; `from` видаляється. Лише одна серія |
| `DELETE /api/tracks/<id>` | трек прибирається з усіх кадрів |
| `POST /api/tracks/undo {undo_id}` | відкат split/merge/delete: відновлює `tracks.json`, polygons/groups і стани всіх кадрів серії |
Ці операції перезаписують і поточний кадр → фронт зберігає кадр перед запитом, після — перечитує полігони й тінь.
**Undo (2026-11-17, гілка `ux-fixes`):** перед split/merge/delete сервер робить знімок (`tracks._snapshot`: текст
`tracks.json` + polygons/groups/стан кожного кадру серії; в пам'яті, останні 30) і повертає `undo_id`. Фронт кладе в
глобальну історію запис `{trackop}`; Ctrl+Z → `/api/tracks/undo` (знімок одноразовий), Ctrl+Shift+Z → операція
повторюється з новим `undo_id`. Раніше ці операції **очищували** історію — видалення полігона перед ними вже не
скасовувалось (скарга мейнтейнера). Знімки живуть до перезапуску сервера.

## 4. Фронт (`editor/tracks.js`)
- Кнопки видно лише доречні (`_tracksUpdateButtons`, лише tool=null): обрано звичайний полігон → «🎞 Трек»;
  полігон треку → «🎞 #id», «⛔ Outside», «✂ Розділити», «🔗 Злити…» (номер через prompt зі списком треків
  серії), «🗑 Трек».
- «📎 До треку…» (`_trackAssign`): обраний звичайний полігон стає формою наявного треку (номер через prompt зі
  списком треків серії) на цьому кадрі — `flags.track_id`, `keyframe=true`; стара форма треку на кадрі видаляється з
  ремапом груп; далі звичайний `_polySave` → `sync_frame` (ключовий кадр). Сценарій: «перемалював клітину №2 — номер
  лишається 2», замість видалити + новий трек + злити.
- «🎞 Трек»: `/api/tracks/new` → `flags.track_id`, `keyframe` → негайний `_polySave` (сервер розносить трек).
- «⛔ Outside» = `_polyDeleteSelectedShape` + save (той самий шлях, що й звичайне видалення; Ctrl+Z повертає).
- Підпис `#id` (`◆` — ключовий кадр) у центрі полігона, `text.polygon-track-label`, розмір шрифту
  `12 * _pxPerCss()` (оновлюється в `_polyResizeVertices`), обводка `calc(3px * var(--zinv))`.

## 5. Експорт / імпорт
- Звичайний експорт кладе `tracks.json` (поряд з labels/group_classes); Split-пакет — теж.
- Імпорт (`_merge_workspace_meta`): локального `tracks.json` нема → копія; є і відрізняється → **лишаємо свій**,
  відповідь `tracks_kept_local` → попередження в toast (злиття номерів треків між датасетами не підтримується).
- Фінальний датасет (`bake_all.py --pack`): `tracks.json` + `tracks/<серія>_mot.txt` — MOT
  (`кадр,трек,x,y,w,h,1,-1,-1,-1`, bbox полігона; кадр = число з імені фото), лише обрані фото.
  Полігони в `polygons/<stem>.json` deliverable несуть `flags.track_id`.
